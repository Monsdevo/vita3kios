1. FIXED PRODUCT DEFINITION
==============================================================================

Identity:
  - Product name: vita3kios
  - Brand reading: "vita-3-kios"
  - Swift module and target name: Vita3KiOS
  - Bundle identifier: selected during signing; no personal Team ID is stored.

Core product:
  - Deliver the open-source Vita3K core in an Apple-native arm64 iPhone/iPad app.
  - Use a clear, restrained, accessible SwiftUI interface owned by this project.
  - Import legally obtained user content through Files, show it in a native
    library, and boot it.
  - Integrate video, audio, Vita touch surfaces, physical controllers, device
    motion, and iOS lifecycle behavior.
  - Provide two explicit boot modes:
    1) Direct Game Mode boots a selected installed title without opening SceShell.
    2) System Software Mode runs the authentic firmware-provided SceShell/
       LiveArea environment and can launch installed titles from that shell.
  - Firmware installation alone never proves System Software Mode. Success means
    the real firmware UI boots interactively, launches a title, and returns.
  - Do not publish version 1.0 before milestone MSYS passes. Any earlier Direct
    Game technical alpha must state that System Software Mode is incomplete.
  - Settings are not a simple toggle page. Support global, Direct Game, System
    Software, and title profiles; Basic/Advanced/Developer views; search,
    explanations, reset, validation, and safe migration.
  - Both boot modes show a small readable top-right performance HUD by default.
    The HUD is configurable and may be disabled; Compact is the default preset.

Initial distribution target:
  - Permanently user-built, developer-signed, or sideloaded IPA on a physical device.
  - Explicitly enabled JIT for the performance build.
  - App Store and TestFlight distribution are not product targets.

Out of scope:
  - Distributing Sony firmware, games, licenses, keys, or decryption data.
  - Adding a piracy store, game-download catalog, or similar content source.
  - Porting or embedding the desktop Qt UI.
  - Claiming full Vita3K compatibility at launch.
  - Treating Simulator results as physical-device emulation evidence.
  - Rewriting Vulkan in native Metal without a measured blocker.

Initial technical decisions:
  - UI: SwiftUI with small UIKit/MetalKit bridges where required.
  - Core: pinned upstream Vita3K C++ built with CMake.
  - Swift/C++ boundary: versioned C ABI; Swift never owns raw C++ objects.
  - CPU: Dynarmic A32-to-A64 first.
  - GPU: Vita3K Vulkan renderer through MoltenVK and CAMetalLayer first.
  - Native services: GameController, CoreMotion, AVFoundation/AudioToolbox,
    os/log, UIKit scene lifecycle, and Files document picker.
  - Provisional minimum: iOS 17.4. Raise it only from Phase 2A measurements;
    lower it only with test evidence.
  - Runtime architecture: arm64 physical devices only. Simulator may host UI and
    parser tests but is not a supported game-runtime target.

License policy:
  - Preserve Vita3K GPL-2.0 obligations for the combined application and core.
  - Make corresponding source, licenses, commit IDs, and modifications available
    with every distributed binary.
  - Inventory all third-party licenses and complete a release legal review.
  - This roadmap is not legal advice.

Layers:

  A. Native App
     - SwiftUI library, settings, import, error, diagnostics, and onboarding.
     - Select SwiftData/Core Data only after measuring the model; never store game
       files in the database.
     - Own app lifecycle, accessibility, localization infrastructure, and UI state.

  B. Session Coordinator
     - One emulation session state machine:
       idle -> preparing -> waitingForJIT -> booting -> running <-> paused
       -> stopping -> idle, with controlled cleanup after errors.
     - Never block the UI thread or allow a second concurrent title session.
     - Preserve explicit directGame(titleID) and systemSoftware session types.
     - Preserve shell -> title -> shell ownership of saves and configuration.

  C. Vita3KBridge C ABI
     - create/destroy, initialize/shutdown, install/enumerate, boot/pause/resume/stop.
     - Frame/surface, input, audio, log, progress, metrics, and error callbacks.
     - Typed errors; no C++ exception may cross the ABI.
     - ABI version and capability queries.
     - Separate boot_title and boot_system_software entry points.
     - Versioned settings descriptors, effective values, validation, and mutation.
     - HUD snapshots for supported frame, CPU/GPU/JIT, memory, thermal, and audio data.

  D. iOS Platform
     - Sandbox paths, atomic writes, temporary storage, and recovery.
     - CAMetalLayer/MoltenVK surface and executable-memory/JIT adapters.
     - GameController, CoreMotion, touch, audio session, and low-latency output.
     - Foreground/background, interruption, thermal, and memory-pressure events.

  E. Upstream Vita3K Core
     - CPU, kernel, HLE modules, GXM/shader translation, Vulkan renderer,
       package/firmware handling, and VFS.
     - Exclude Qt GUI and desktop main() from the iOS binary.
     - Treat installing LLE firmware modules and booting the authentic firmware
       shell as separate capabilities with separate evidence.

Dependency strategy:
  - Pin upstream and recursive dependencies by Git commit; do not copy source trees.
  - Keep iOS-specific code in PlatformIOS/Bridge where possible.
  - If upstream files require changes, use small versioned patches.
  - Exclude Qt, Discord SDK, OpenGL, and desktop-only components from iOS.
  - Audit every iOS dependency for arm64 slices, exceptions/RTTI, license,
    static/dynamic linkage, public API usage, and signing behavior.

5. MAJOR RISKS AND PREDECIDED RESPONSES
==============================================================================

R1 — iOS JIT restrictions
  Impact: Dynarmic may fail or run too slowly without JIT.
  Response: close the isolated Phase 2A gate first; use external StikDebug as the
  initial route; show JIT readiness before boot.

R2 — Tight Qt/desktop coupling
  Impact: iOS compile/link complexity.
  Response: derive a headless API from existing interface/Android patterns; never
  put Qt in the iOS application.

R3 — Vulkan/MoltenVK gaps
  Impact: shader errors, missing extensions, or poor performance.
  Response: start from upstream Apple Vulkan behavior, record capabilities and
  captures, and consider native Metal only after a measured blocker.

R4 — Sandbox and lifecycle
  Impact: provider access loss, background failures, corrupt import/save state.
  Response: staging and atomic moves, relative identities, lifecycle state machine,
  and interruption/recovery tests.

R5 — Memory and thermal limits
  Impact: jetsam, throttling, audio/frame loss.
  Response: physical-device Instruments evidence, budgets, conservative defaults,
  and controlled response to pressure.

R6 — Fast upstream change
  Impact: patch decay.
  Response: exact submodule pin, small commits, regression tests, planned sync.

R7 — Licensing and distribution
  Impact: inability to distribute or GPL violation.
  Response: corresponding source mapping, manifest, notices, and a documented
  self-sign/sideload release gate.

R8 — Content and trademarks
  Impact: legal and project risk.
  Response: no firmware/games/keys, user-owned dumps only, clear non-affiliation,
  and no unauthorized Sony assets.
